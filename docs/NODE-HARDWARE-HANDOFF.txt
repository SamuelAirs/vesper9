SAM'S FINISHED NODE — REUSE BRIEF FOR ANOTHER PROJECT
Prepared 2026-10-04. Target: board 2, the assembled four-lamp node.

START HERE

Use the externally accessible native USB connector. Sam does not want to reopen
the case to expose the separate COM/UART connector. The installed firmware
already exposes the button, four RGB lamps, board RGB accent, acoustic taps and
microphone audio over native USB using a small binary serial protocol. Ordinary
reuse can be implemented on the host without reflashing or rewiring the node.

Treat this as a general-purpose physical controller and light/audio peripheral.
Your new project's engine, user interface, gestures and action mapping are your
choice. Vesper's one-button menu gestures are application policy, not hardware
requirements. Keep the existing case and wiring, and make generic taps useful;
left/right recognition is an optional calibrated feature, not guaranteed input.

WHAT IS IN THE CASE

- ESP32-S3 N16R8 development board: 16 MiB flash and 8 MiB PSRAM, according to
  the assembled-node records. Firmware uses ESP-IDF, not Arduino or MicroPython.
- One momentary arcade button. Both press and release edges are available, so
  the host can distinguish taps, holds, double presses and combinations.
- Four separate RGB lamps, physically ordered left to right. All twelve color
  channels are independently controllable at 0..255. These are discrete LED
  legs driven with PWM, not an addressable strip.
- Two INMP441 digital I2S microphones, left and right, used for sound and
  acoustic case-tap detection. There is no dedicated directional tap switch,
  accelerometer or force sensor in this documented assembly.
- One separately addressable WS2812 RGB LED on the ESP32 development board,
  used as an optional accent. It is not a fifth main lamp. Power and UART TX/RX
  indicator LEDs are not independent application-controlled lights.
- No temperature/humidity sensor on board 2. Old SHT3x documentation describes
  board 1. The Pi CPU temperature shown by Vesper is unrelated to node sensing.
- No speaker-output command in this node firmware. Vesper plays audio through
  the host/deck. Do not assume the node is a USB sound card or contains a
  firmware-controlled audio-output device.

USB CONNECTION — THE NORMAL PATH

The accessible connector uses the ESP32-S3 USB Serial/JTAG peripheral and its
CDC-ACM serial interface. It carries Vesper protocol v1, not plain-text commands,
HID gamepad events, MIDI, or USB Audio Class streams. No UART bridge is required.

Linux normally names it /dev/ttyACM*; Windows names it COM*. A Windows COM7-style
device name DOES NOT mean you must use the inaccessible physical COM connector.
Select the Espressif USB Serial/JTAG device belonging to this node.

Last verified Pi device path:
  /dev/serial/by-id/usb-Espressif_USB_JTAG_serial_debug_unit_DC:DA:0C:14:8F:C0-if00
Recorded board identity/MAC: dc:da:0c:14:8f:c0.
Use identity-based discovery; ttyACM numbers and Windows COM numbers can change.

The host serial code uses 921600 baud, 8N1, no flow control. Native USB ignores
the UART baud-rate setting, but retaining 921600 matches the existing adapter.
Avoid opening with DTR/RTS asserted or gratuitously toggling them: the current
host sets both false before opening. Use a data-capable USB cable.

The inaccessible connector is a separate UART bridge path, UART0 on GPIO43/44.
It serves the same frames but is not needed for this project. Do not have two
hosts/controllers competing: node replies follow the last valid host link.

If new firmware ever becomes necessary, native USB has previously been used
successfully to flash this exact board without touching its buttons (historical
2026-10-02 handoff). Preserve working USB Serial/JTAG support and GPIO19/20.
Disabling USB or entering incompatible sleep modes can lose the connection;
recovery from some bad firmware may require GPIO0/reset access inside the case.
Therefore keep the installed firmware for host-side reuse whenever possible.
Espressif confirms serial operation and flashing over this connector [USB].

CORRECTED GPIO MAP — BOARD 2 ONLY

This is the EFFECTIVE RGB order in the firmware, confirmed by the historical
one-channel-at-a-time lamp check. Sam's original wiring table labelled green
and blue the other way around. Do not swap them again in your host software:
send ordinary R,G,B bytes and let the installed firmware map pins.

Component                    GPIOs
Lamp 1, left — R / G / B       7 / 16 / 15
Lamp 2       — R / G / B      17 /  8 / 18
Lamp 3       — R / G / B       9 / 11 / 10
Lamp 4, right— R / G / B      13 /  3 / 14
Left mic    — BCLK / WS / SD   4 /  5 /  6
Right mic   — BCLK / WS / SD  47 / 45 / 21
Button input                 12, active-low with internal pull-up
Button return                46, configured output-low by the firmware
Board WS2812 data             48; protocol RGB, physical LED wire order GRB
Native USB D- / D+            19 / 20
UART0 TX / RX, not required   43 / 44

Button return is an actual GPIO connection, not a license to change that pin's
state. The switch closes between GPIO12 and GPIO46. GPIO3, 45 and 46 have boot
strapping roles: preserve this known-working wiring and initialization. On the
corrected lamp map GPIO3 is lamp 4 GREEN, despite the older wiring table's label.

The microphones use 3.3 V and common ground. Lamps share common ground and use
active-high color legs with existing current limiting. The historical 430-ohm
resistor statement belongs to board 1; board-2 resistor values, exact board
vendor/schematic, current draw and enclosure dimensions have not been separately
verified for this brief. None is needed to use the existing USB interface.

Firmware assigns eight color legs to LEDC and the remaining four to MCPWM.
PWM is 4 kHz, with 10-bit LEDC and a 1000-count MCPWM period. Main-lamp values
use approximately gamma-2.2 brightness mapping. Board RGB is a separate RMT
WS2812 output. Keep it subtle by choice; the protocol does not force that.

TAPS AND AUDIO: WHAT THE NODE ACTUALLY DOES

The left I2S controller generates clocks; firmware mirrors them to the right
microphone's clock pins and receives that port in slave mode. This is intended
to align both channels. Check STATUS.mic2 diagnostics and actual sample behavior
if building timing-sensitive audio features; a second-port failure can degrade
operation even when the compile-time profile says two microphones.

Audio is 16 kHz signed 16-bit little-endian PCM. Mono AUDIO normally contains
320 samples (20 ms); stereo AUDIO2 normally contains 160 left/right frames
(10 ms) per packet, two packets per 20 ms read. Both start with a u32 sample/
frame index. Use indices to detect gaps and handle wrap; USB arrivals are not
the sampling clock. The two stereo packets can arrive together after one
20 ms read; do not assume evenly spaced arrivals. Firmware discards the first
300 ms when acquisition starts and applies a roughly 25 Hz DC-blocking
high-pass. It is not studio-calibrated spatial audio.

Case taps are detected acoustically on the left microphone; the right channel
supplies additional clip information for host classification. Existing behavior:
- Verdict approximately 90 ms after onset, plus buffering/USB/host latency.
- Minimum 150 ms between detected onsets. Do not assume a faster double tap
  produces two events. A clap or another sharp sound can also count; the
  detector's optional brightness rejection is currently disabled.
- Default Vesper threshold 4000; less-sensitive 8000, more-sensitive 3000.
  Firmware accepts zero (disabled) or 256..32767.
- Firmware suppresses taps within 60 ms of button edges. Vesper's host adds
  suppression while the button is held and through 200 ms after an edge.
  Consequently button-hold-plus-case-tap controls need explicit design work
  in a new host; current Vesper filtering can discard those intended taps.
- The host also suppresses taps during its own low tones below 140 Hz, with
  a 250 ms tail. This is in web/engine/audio.js and web/main.js, NOT entirely
  in the node firmware. A new application that plays bass through the case
  must carry over/test this protection. There is no universally reliable
  hardware distinction between a game sound, clap and intentional case tap.

IMPORTANT: MIC=0 disables continuous audio STREAMING. If knock detection is
enabled, microphones still acquire samples. On this two-mic firmware, an
accepted tap can send a short stereo KNOCK_CLIP immediately before KNOCK even
with MIC=0. To stop both functions send MIC=0 AND KNOCK_SET=0, and account for
any already in-flight packets. This does not physically remove microphone power.
Do not repeat older comments claiming that only an event, never sound, leaves
the node in tap mode. Vesper extracts features locally and removes raw clips
before browser delivery; that privacy behavior belongs to its host service.

Generic taps, including comfortable back-of-case taps, are Sam's default.
Optional left/right classification uses the two-mic clip plus host calibration;
firmware does not emit a trusted left/right label. Back taps cannot reliably
be separated from sides. Sam reports useful left/right distinction, but mixed
posture, case acoustics and speaker volume still need human verification.

WIRE PROTOCOL QUICK REFERENCE

Reuse vesper/protocol.py (small standard-library codec) instead of guessing.
All numeric fields are little-endian. A frame is:
  'V9' | u8 version=1 | u8 type | u16 sequence | u16 payload_length
       | payload | u16 CRC
Payload maximum 768 bytes; total frame length payload+10. CRC-16/CCITT-FALSE:
poly 0x1021, init 0xFFFF, no reflection/final XOR; CRC covers version through
payload, excluding magic. ASCII '123456789' -> 0x29B1. Preserve partial reads
and resynchronize after corrupt frames; sequence numbers wrap at 65536.

Host -> node (decimal types):
16 PING       empty; node returns STATUS. Send about once per second.
17 LEDS       12 u8 values: R1,G1,B1,R2,G2,B2,R3,G3,B3,R4,G4,B4.
              Legacy 9 values duplicate the middle triplet across lamps 2/3.
18 MIC        one u8: 0 stop streaming; 1 mono left; 2 stereo.
19 ARM        u32 trial_id, u32 delay_ms, u8 logical_light, u8 R,G,B.
              Delay 250..10000 ms; logical light 0..2, middle lights both
              physical middle lamps. Use LEDS for independent four-lamp control.
20 CANCEL     empty; cancels queued cue/pattern, does not itself turn lights off.
21 PATTERN    u8 repeats(1..8), u8 count(1..16), then count steps of
              u16 duration_ms(10..10000) + 12 RGB bytes (or all 9-byte steps).
22 KNOCK_SET  u16 threshold; zero disables.
23 BOARD_LED  three u8 values R,G,B, independent of the four main lamps.

Node -> host:
1 HELLO       UTF-8 JSON status at startup.
2 BUTTON      u64 initial_edge_at_us, u8 pressed; emitted after 8 ms stable
              debounce, timestamped at the original edge, not delivery time.
3 SENSOR      legacy board-1 temperature/humidity; not a board-2 capability.
4 AUDIO       u32 first_sample_index, followed by mono s16 samples.
5 CUE         u32 trial_id, u64 activated_at_us.
6 STATUS      UTF-8 JSON, about once/second and after PING.
7 ACK         u16 original_sequence, u8 result, u8 original_command_type.
              result 0 accepted, 1 invalid payload, 2 unknown command.
8 KNOCK       u64 at_us, u16 peak, u8 hf. Older compatibility form omits hf.
9 AUDIO2      u32 first_frame_index, followed by interleaved L,R s16 pairs.
10 KNOCK_CLIP u64 at_us, u8 pre_frames=16, u8 channels=2, 176 stereo s16
              frames: 714-byte payload. Match its timestamp to the next KNOCK.

BUTTON, KNOCK and CUE timestamps share the node's monotonic microsecond clock;
that clock restarts on reboot. Track connection/boot generations and cancel
unfinished holds/actions on disconnect. Use device timestamps for event timing,
not differences between device time and the host wall clock. Button held at
boot/link-loss is inhibited until released. ACK for MIC is not proof of live
capture; check STATUS.mic, stereo and mic2 plus incoming audio.

STATUS fields worth checking: fw, board=2, lamps=4, mics=2, link='usb', mic,
stereo, mic2, slots, button, leds, board_led, knock, audio_drops and rx_crc.
After three seconds without a valid host frame, firmware disables streaming
and taps, cancels cues/patterns and turns main/board lights off. Reapply explicit
settings after reconnect; do not silently restart audio recording.

Command interaction: LEDS cancels PATTERN but leaves an ARM cue scheduled.
On an agreed controller takeover or exit, send CANCEL and explicit main-lamps
and board-LED off; do not assume a new LEDS command cancels every previous job.

HOW TO INTEGRATE WITHOUT DISTURBING VESPER

1. Read-only discovery while Vesper owns the port: use its loopback HTTP
   GET http://127.0.0.1:8799/api/system and /api/state, or inspect OS port names.
   From Windows (one command):
   ssh -o BatchMode=yes -o ConnectTimeout=5 pi5 "curl --max-time 3 -fsS http://127.0.0.1:8799/api/system"
   The endpoint is on the Pi's loopback interface; Windows localhost is a
   different machine unless a deliberate SSH tunnel is established.
2. For a Vesper-integrated app, use its app context/light ownership and /ws
   service. Commands include leds(values[12]) and board_led(values[3]); only
   the controller may act. Additional browser tabs are observers. Reuse
   source-owned edges, cancellation and lifetime cleanup.
3. For an independent app, write a small host adapter using the serial codec.
   Coordinate stopping the existing serial owner before opening this USB
   device. Do not run node-probe.py or another serial monitor concurrently
   with vesper.service. Preserve its current source, saves and configuration.
   Changing controller ownership/stopping Vesper is not part of this brief.
4. Initially keep MIC and KNOCK_SET off. Confirm HELLO/STATUS identity; then
   enable only the features that project actually needs. Keep reading packets
   and sending PING. Treat tap interpretation, calibration, sound suppression,
   input bindings and game rules as host responsibilities.
5. A later agreed physical check should cover each RGB channel at low
   brightness, board accent, button edges, comfortable back taps, optional
   sides, audio only if needed, reconnect cleanup and false taps from sound.
   Do not interpret simulator success as those checks being complete.

FLASHING IS A SEPARATE JOB, USUALLY UNNECESSARY FOR REUSE

Do not flash firmware/prebuilt/*.bin onto this node: those are board-1 version
0.1.2 artifacts, despite the repository/application being labelled 0.2.0.
Source build profile must explicitly be NODE_BOARD=2; default is board 1.
The recorded toolchain is ESP-IDF 5.4.2, with scripts/build-firmware.sh 2.
Build on Windows/Windows-hosted WSL, not the battery-powered Pi.

Before any authorized replacement, identify this board, preserve a NEW verified
full 16 MiB (16,777,216-byte) flash backup with SHA-256 and restore command,
and preserve USB recovery. scripts/flash-node.py enforces board/MAC and backup
checks; understand its behavior before using it. Historical backup
/home/sam/VESPER-9-v0.2.0-Claude/vesper9/backups/node2-as-found-20261002-125315.bin
is the factory MicroPython image, not a backup of the present Vesper firmware.
Its current existence/hash has not been checked here. Never publish flash
backups, credentials, calibration/save databases, recordings or speech models.
